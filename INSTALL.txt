Awoki Installation Guide

This is the preferred Docker/OpenCode-over-SSH installation.
For the conceptual overview and first-use workflow, read README.md first.
For dense operational detail, see docs/OPERATOR_REFERENCE.md.
Release metadata is authoritative in pyproject.toml and .harness/manifest.json;
release history belongs in CHANGELOG.md. This guide intentionally does not pin
an Awoki release number in its title.

Topology

  host
    -> browser -> 127.0.0.1:4096 -> authenticated OpenCode Web
    -> SSH -> awoki-opencode-ssh container (attached TUI + Awoki MCP)
    -> optional Burp MCP on host loopback
    -> optional remote embedding/reranker endpoints

  Docker network
    -> qdrant
    -> awoki-opencode-ssh

No Docker socket is mounted into the OpenCode container.
No Docker-in-Docker or privileged mode is required.

Requirements

Install on the host:

  Docker Desktop / Docker Engine
  Docker Compose v2
  git
  ssh + ssh-keygen (OpenSSH client tools)
  make
  Python 3.12+

Check:

  docker --version
  docker compose version
  git --version
  ssh -V
  command -v ssh-keygen
  python3 --version

Replacing or recloning an existing checkout

For a guided install, prefer:

  ./install-awoki.sh

The interactive installer asks before changing an existing runtime conflict. A
same-path container whose Awoki runtime-instance ID belongs to a replaced checkout
can be safely removed without -v; named volumes and host data are preserved. A
different live checkout is never stopped or replaced by the low-level launcher.
The interactive wizard instead offers three explicit choices: stop only that other
checkout's running Awoki/Qdrant containers and continue (containers/volumes/data
are preserved), keep both runtimes and select a different Compose project plus free
SSH/Web/Qdrant/Lavish ports, or abort with both checkouts untouched.

For a release ZIP, the optional host bootstrap can perform the outer replacement
steps before the in-checkout wizard:

  ./bootstrap-awoki.sh /path/to/awoki-release.zip /path/to/awoki
  ./bootstrap-awoki.sh https://example.invalid/awoki.zip /path/to/awoki

If the target exists it offers to move it to a timestamped backup or choose a new
target. It does not silently rm -rf an existing checkout. Existing Docker
containers are intentionally left for the runtime-instance conflict check, which
can then explain exactly what belongs to the previous checkout. A normal GitHub
Download ZIP has no .git history; the bootstrap can create a clearly labeled local
baseline HEAD for running/testing. Use a real git clone for upstream history,
development, or publishing.

Fresh install — interactive (recommended for a person)

1. Enter the writable Awoki Git checkout.

2. Run:

  ./install-awoki.sh

The wizard covers the former manual steps: create/refresh .env, select Compose
project/SSH/Web settings, optionally configure embeddings and reranker, initialize
the runtime layout/SSH keys, and prepare the ignored OpenCode user config at:

  .opencode-state/config/opencode.jsonc

That is the recommended file in which to paste your custom OpenCode provider/model
configuration. Before any Docker build/start the installer validates it and shows
a pre-build review. The menu is intentionally non-eager:

  1) edit OpenCode user/provider config (NO build)
  2) edit .env (NO build)
  3) edit Awoki's tracked opencode.jsonc (advanced; NO build)
  4) re-run validation (NO build)
  5) BUILD/START Docker now
  6) stop with configuration saved

Even option 5 requires a final yes/no confirmation. Docker conflict reconciliation
is delayed until that build confirmation, so reviewing/editing configuration does
not tear down an older runtime. If conflict resolution changes `.env` -- for example when keeping two Awoki
runtimes alive and selecting alternate SSH/Web/Qdrant/Lavish ports -- the wizard
runs static validation again, shows the updated redacted review, and asks again.
After startup it can run OpenCode's provider credential-login and MCP-add workflows
and offers the broader runtime check. Independently of that choice, the installer
always runs a mandatory SSH-readiness gate before it can report success. That gate
requires the host private/public key pair to exist and match, requires the running
container to authorize the same public key, and performs a real BatchMode public-key
login. --skip-runtime-check does not disable this SSH gate.

Use:

  ./install-awoki.sh --configure-only

to save configuration and initialize the layout without building/starting.


OpenCode custom provider/model configuration

Awoki intentionally separates its tracked project configuration from your personal
OpenCode provider configuration.

Edit this on the macOS host:

  .opencode-state/config/opencode.jsonc

OpenCode sees the same bind-mounted file inside the container at:

  /home/op/.config/opencode/opencode.jsonc

Use this file for custom `provider`, model, and other user-level OpenCode settings.
It is ignored by Git and excluded from the Docker build context. The tracked root
`opencode.jsonc` belongs to the Awoki project/runtime contract (Awoki MCP, direct
Burp MCP, instructions, permissions, compaction). `opencode.container.jsonc` is
not the personal-provider configuration location.

During first install, choose installer option 1 at the OpenCode/provider step and
paste your JSONC into the editor. The installer validates syntax and returns to the
pre-build menu; it will not start Docker until you explicitly choose BUILD/START.

To change the custom provider config after installation:

  cd /path/to/awoki
  $EDITOR .opencode-state/config/opencode.jsonc
  make opencode-user-config-check
  make opencode-config-reload

The reload path does not rebuild the Docker image. The user config directory is a
runtime bind mount. The helper restarts only the OpenCode SSH/Web service and then
checks the runtime. This restart ends active TUI/Web backend/tmux processes in that
container, so reconnect afterward; persisted OpenCode/Awoki data remains. If the
runtime is currently stopped, no restart is needed: the next start reads the file.

For provider credentials, prefer OpenCode's credential flow when supported:

  make opencode-auth

OpenCode stores its credential state under its persisted application-data mount,
separate from the JSONC. If your custom provider requires a literal credential in
the user JSONC, that file is still plaintext on the host even though Awoki ignores
it in Git and Docker builds.

Fresh install — deterministic/manual (automation)

1. Enter the writable Awoki Git checkout.

2. Create the local environment file:

  cp .env.example .env

Semantic retrieval is optional. Configure AWOKI_EMBEDDING_* only when you intend
to authorize remote embeddings/vector materialization. Configure AWOKI_RERANK_*
only when you intend to use a remote reranker.

3. Initialize runtime directories and SSH material BEFORE Docker starts:

  ./init-awoki.sh

4. Run host preflight:

  make dependencies-check
  make dev-preflight

5. Build/start the preferred OpenCode-over-SSH runtime:

  make install-opencode-ssh

6. Validate only after step 5 succeeds:

  make opencode-runtime-check

If make install-opencode-ssh / make opencode-ssh-up fails, stop there and fix the
startup failure first. Do not run opencode-runtime-check against an old or partially
started container; secondary runtime errors can hide the original startup problem.

7. Confirm the hard SSH client contract (the guided installer already does this):

  make opencode-ssh-client-check

Then connect using the absolute-path SSH command printed by the installer. Example:

  ssh -i "/path/to/awoki/.ssh-container/id_ed25519" -o IdentitiesOnly=yes -o UserKnownHostsFile="/path/to/awoki/.ssh-container/known_hosts" -o StrictHostKeyChecking=accept-new -p 2222 op@127.0.0.1

8. Inside the container:

  cd /awoki
  tmux new -A -s awoki
  awoki-opencode

`awoki-opencode` uses `opencode attach` when Web is enabled, so browser and TUI
share sessions/state. It supplies Basic-Auth through process environment, not a
`--password` argument. With AWOKI_OPENCODE_WEB_ENABLED=0 it runs standalone
`opencode`. /awoki/opencode.jsonc remains the project configuration and loads
Awoki through the reviewed MCP launcher.

Why tmux

  - tmux is recommended, not required by Awoki.
  - it keeps the OpenCode terminal alive across SSH disconnects;
  - `tmux new -A -s awoki` creates the named session or reattaches to it;
  - detach without stopping OpenCode with Ctrl-b d or Ctrl-a d;
  - tmux sessions do NOT survive container recreation.

Daily start / reconnect

From the host:

  make opencode-ssh-up
  make opencode-runtime-check
  ssh -i .ssh-container/id_ed25519 -p 2222 op@127.0.0.1

Inside the container:

  cd /awoki
  tmux new -A -s awoki

If the attached TUI is not already running in the tmux session:

  awoki-opencode

If SSH drops, reconnect and repeat only the SSH + tmux commands. Do not restart or
recreate the container merely to recover the terminal.

A practical tmux layout is:

  window 1: OpenCode
  window 2: shell / exact searches / repository inspection
  window 3: tests or long-running commands
  window 4: logs

Stop the deployment only when you actually want the container/Qdrant services down:

  make opencode-ssh-down

After `make opencode-recreate`, the old tmux/backend processes are gone. The new
container starts a fresh Web backend against the persisted OpenCode state. SSH in,
run `tmux new -A -s awoki`, and start `awoki-opencode` again. Durable Awoki/project/
OpenCode state lives on the configured host mounts; tmux itself is only a terminal
session wrapper.

Rebuild after an Awoki update

Latest / untested OpenCode stack:

  make opencode-recreate \
    OPENCODE_RECREATE_ARGS="--validate --no-cache --opencode-latest"

Operator-selected safe version:

  make opencode-recreate \
    OPENCODE_RECREATE_ARGS="--validate --no-cache --opencode-safe <VERSION>"

Safe mode means "use exactly the version I selected". Awoki does not automatically
promote any version to known-good.

Create a first project

From the writable host checkout:

  python3 .harness/project.py create review1

Clone a target repository into the managed project:

  git clone <repository-url> workspace/projects/review1/repo/target

Register that exact root:

  python3 .harness/project.py repo-add \
    --default \
    review1 \
    target \
    repo/target

Inside OpenCode:

  Resume project review1.

or precisely:

  project_open(name="review1", create_if_missing=false)
  project_repo_list(name="review1")

Prepare repository state

Local/structural only (no remote embedding authorization):

  repository_prepare_start(
    name="review1",
    repo="target",
    mode="local",
    resume_goal="continue the review after LOCAL_READY"
  )

Full semantic readiness (explicitly authorizes configured semantic materialization
for this managed source):

  repository_prepare_start(
    name="review1",
    repo="target",
    mode="full",
    resume_goal="continue the review after FULL_READY"
  )

The returned rpr_ job is detached. Do not have the model tight-poll it. Check later
with repository_prepare_status or use the bounded continuation mechanism.

Start the first real review

Once the repository is LOCAL_READY (or FULL_READY when semantic materialization was
explicitly requested), talk to OpenCode normally. For example:

  Review authentication in this repository. Trace credential handling into
  authorization, identify configuration-dependent reachability and fail-open/fail-closed
  behavior, and distinguish verified source facts from hypotheses or deployment gaps.

For a multi-step review, the agent should keep a small outcome-oriented OpenCode TODO
working set rather than copying every intermediate thought. Awoki mirrors the active
work and useful durable evidence so automatic OpenCode compaction can continue from
project state instead of treating chat history as canonical. You normally do not need
to do anything special when compaction happens.

Use source tools by intent:

  conceptual/architectural discovery  -> Awoki codebase_search
  simple known string/symbol           -> OpenCode Grep
  structured exhaustive exact search   -> Awoki code_exact_search
  stronger materialized exhaustive job -> Awoki code_text_search

OpenCode version policy

Default fresh build:

  latest / untested

Explicit last-known-good rollback:

  make opencode-recreate \
    OPENCODE_RECREATE_ARGS="--validate --no-cache --opencode-safe <VERSION>"

Normal make opencode-ssh-up does NOT resolve a new OpenCode release. It starts the
already built image.

Environment notes

The stock .env.example keeps:

  AWOKI_OPENCODE_WEB_ENABLED=1
  AWOKI_OPENCODE_WEB_PORT=4096
  AWOKI_OPENCODE_WEB_USERNAME=opencode
  AWOKI_OPENCODE_WEB_PASSWORD=
  AWOKI_RERANK_ENABLED=0
  AWOKI_CODE_RERANK_TIMEOUT_SECONDS=

Leaving the Web password empty is intentional: the host launcher generates and
persists a strong random secret. An explicit plaintext override is supported for
local testing, but OpenCode Basic Auth cannot consume a password hash. The stock
path therefore keeps plaintext out of Compose metadata/argv and only in the 0600
host auth file plus container `/run` tmpfs/process environment.

An empty AWOKI_CODE_RERANK_TIMEOUT_SECONDS inherits AWOKI_RERANK_TIMEOUT_SECONDS.

After changing retrieval/Qdrant/reranker configuration, recreate the OpenCode SSH
runtime and start a fresh OpenCode process. Do not manually source
/run/awoki/runtime.env.

Troubleshooting

1. Dirty Git checkout during an update

  git status --short

Do not overwrite local changes blindly. Commit/stash/restore them intentionally.
Awoki's release bundle install instructions assume a clean worktree.

2. Invalid opencode.jsonc

  python3 .harness/validate.py

If the local opencode.jsonc modification is not needed and the bundled copy is the
wanted configuration:

  git restore opencode.jsonc

Then validate/recreate again.

3. SSH port already in use

Set in .env:

  AWOKI_OPENCODE_SSH_PORT=2224

Then:

  make opencode-ssh-up

Connect using the new port.

4. SSH public-key failure

Stop the OpenCode SSH runtime, preserve anything you need, then regenerate only the
local SSH material:

  make opencode-ssh-down
  rm -rf .ssh-container
  ./init-awoki.sh
  make opencode-ssh-up

5. Runtime logs

  docker compose -f docker-compose.opencode.yml logs --tail=200 awoki-opencode-ssh
  docker compose -f docker-compose.opencode.yml logs --tail=200 qdrant

Awoki MCP local stderr is also mirrored to:

  .harness/state/mcp-local.stderr.log

Security note

Awoki filters provider credentials from repository-facing Git/search subprocesses,
but this is defense in depth, not a same-user sandbox. Do not execute hostile target
code inside a credential-bearing OpenCode container. Use a separate credential-free
sandbox for untrusted execution.
